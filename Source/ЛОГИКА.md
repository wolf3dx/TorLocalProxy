# Карта логики TorLocalProxy

Как устроено приложение и почему именно так. Читать до правки кода: половина
решений здесь продиктована ограничениями платформ, и без них выглядит произволом.

---

## 1. Что происходит от нажатия кнопки до рабочего прокси

```
  текст письма с мостами
          │
          ▼
   ┌─────────────┐   []Bridge    ┌──────────┐
   │  bridges    │──────────────►│ torconf  │  генерирует torrc
   └─────────────┘               └──────────┘
          │                            │
          │ какие транспорты нужны     │ адреса запущенных PT
          ▼                            ▼
   ┌─────────────┐   []PTPlugin  ┌──────────┐
   │   ptrun     │──────────────►│  torrun  │  поднимает tor
   └─────────────┘               └──────────┘
   lyrebird, snowflake                 │
   в этом же процессе                  │ адрес control-порта
                                       ▼
                                ┌──────────┐
                                │ control  │  cookie-аутентификация,
                                └──────────┘  события BOOTSTRAP 0→100
                                       │
                                       │ адрес SOCKS5
                    ┌──────────────────┼──────────────────┐
                    ▼                                     ▼
             ┌─────────────┐                     ┌────────────────┐
             │ socksproxy  │  HTTP→SOCKS5        │  tun2socks     │  только
             └─────────────┘  (десктоп)          └────────────────┘  мобильные
```

Всё это связывает `service` — единственный пакет, с которым разговаривают UI
и командная строка.

Порядок важен: транспорты поднимаются **до** tor, потому что их адреса нужно
подставить в `torrc`. Порты транспортов не фиксированы — IPtProxy находит
свободные сам и возвращает их.

## 2. Три ограничения, которые определили архитектуру

Каждое из них стоило бы переписывания, если вспомнить о нём поздно.

### 2.1. iOS запрещает дочерние процессы

Ни `tor`, ни `lyrebird` не могут быть отдельными исполняемыми файлами. Отсюда
два следствия, видных в коде.

**`torrun` — интерфейс, а не функция.** Две реализации: `external` запускает
процесс (десктоп), `embedded` линкует tor библиотекой (мобильные). Выбор
делается на этапе сборки, а не в рантайме.

**`ptrun` использует IPtProxy на всех платформах, включая десктоп.** Соблазн
на десктопе просто запускать `lyrebird.exe` есть, но тогда получится две
разные ветки поведения, и мобильная будет проверяться вдвое реже. Один путь
для всех — дешевле в поддержке. Побочная выгода: рядом с приложением не нужно
класть ни одного постороннего исполняемого файла, и в `torrc` не остаётся ни
одного `exec`.

### 2.2. gomobile bind пропускает не всякий тип

Через границу Go↔Swift/Kotlin проходят только знаковые целые, float, `string`,
`bool`, `[]byte`, `error`, интерфейсы и структуры, у которых все экспортированные
поля и методы тоже из этого набора. Функция возвращает не больше двух значений,
второе обязано быть `error`. **Срезов структур и map нет совсем.**

Отсюда пакет `mobileapi`: тонкая обёртка, где сложные структуры уезжают наружу
JSON-строкой, а события приходят через интерфейс-наблюдатель, реализованный на
стороне Swift и Kotlin.

Поэтому же `Observer` в `service` спроектирован «бедным» с самого начала —
чтобы на этапе 9 он переехал через границу без единой правки:

```go
type Observer interface {
    OnBootstrap(percent int, phase string)
    OnLog(line string)
    OnState(state string)
}
```

`context.Context` через границу тоже не проходит — отмена делается вызовом
`Disconnect()`.

### 2.3. На мобильных локальный прокси не виден другим приложениям

Android и iOS не дают приложению обслуживать чужой трафик через `127.0.0.1`.
Единственный путь — VPN: `VpnService` и `NEPacketTunnelProvider`. Между
TUN-интерфейсом и SOCKS-портом нужен слой tun2socks.

Ядро об этом не знает вообще: оно как отдавало адрес SOCKS5, так и отдаёт.
Разница только в том, кто этот адрес потребляет — пользователь вручную на
десктопе или tun2socks на мобильных.

## 3. Пакеты и зона ответственности

| Пакет | Отвечает за | Не отвечает за |
|---|---|---|
| `bridges` | разбор и проверка строк мостов | сеть, файлы |
| `torconf` | генерация `torrc` | запуск чего-либо |
| `ptrun` | pluggable transports в процессе | tor |
| `torrun` | жизненный цикл tor | транспорты, прокси |
| `control` | control-протокол, события bootstrap | запуск tor |
| `socksproxy` | HTTP→SOCKS5 для десктопа | сам Tor |
| `service` | связывает всё, состояние подключения | UI |
| `mobileapi` | обёртка под gomobile | логика |

Правило: `core` не импортирует ничего из `cmd`, `desktop`, `android`, `ios`.
Проверяется линтером.

## 4. Решения, которые выглядят странно без объяснения

**Мосты разбираются вместе с прозой письма.** Пользователь копирует ответ
`bridges@torproject.org` целиком, а не выковыривает строки вручную. Поэтому
парсер молча пропускает всё, что не похоже на мост, и жалуется только на
строки, которые *задумывались* мостами: начинаются с известного транспорта,
содержат `host:port` или 40 hex-символов отпечатка. Иначе на каждое
«С уважением, Tor Project» сыпалась бы ошибка.

**Имя хоста уходит в SOCKS как есть.** Резолвить его локально нельзя — DNS-запрос
ушёл бы мимо Tor и выдал, куда пользователь идёт. В коде это значит: адрес
передаётся типом `0x03` (доменное имя), а не `0x01` (IPv4). Проверяется
отдельным тестом.

**Прогресс контролируется на застревание.** Если процент не меняется 90 секунд,
подключение прерывается с внятным текстом. Без этого пользователь с
заблокированными мостами смотрит на неподвижную полосу до самого таймаута и не
понимает, что делать. Застревание на 5–14 % означает, что мост не отвечает;
на 25–75 % — что мост отвечает, но сеть режет трафик.

**Отсутствие транспорта диагностируется до запуска tor.** Иначе tor молча
стартует, не может выполнить `ClientTransportPlugin` и падает с ошибкой,
по которой ничего не понять.

**HTTP-прокси читает сокет без буферизации.** Буферизованное чтение заголовков
захватывает начало тела запроса, и оно теряется при переходе на перекачку
байтов. В Python это `rbufsize = 0`, в Go — не оборачивать соединение в
`bufio.Reader` дальше заголовков.

## 5. Прототип на Python

`Prototype-Python/` — работающая реализация всего, кроме мобильных платформ.
Она не выбрасывается по двум причинам.

**Эталон логики.** Разбор мостов, генерация `torrc` и HTTP-мост переносятся
в Go почти дословно; таблица соответствий файлов — в `PLAN.md`, раздел 4.

**Испытательный стенд.** `tests/fake_tor.py` изображает tor: control-порт с
cookie- и SAFECOOKIE-аутентификацией, события BOOTSTRAP от 0 до 100, рабочий
SOCKS5, имитация падения. Go-тесты гоняются против той же заглушки — это
экономит день работы и заодно проверяет, что обе реализации понимают протокол
одинаково.

Отличие прототипа от целевой версии одно, но принципиальное: он запускает tor
и транспорты отдельными процессами и потому требует Tor Expert Bundle рядом.
Целевая версия этого не требует — см. 2.1.
