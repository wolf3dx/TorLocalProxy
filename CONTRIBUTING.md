# Как здесь работать

Проект собирается по `PLAN.md`: один этап — одна сессия, следующий этап не
начинается, пока тесты текущего не зелёные. До правки кода читается
`Source/ЛОГИКА.md` — половина решений продиктована ограничениями платформ и
без них выглядит произволом.

## Что нужно на машине

- **Go 1.24+** — `go version`
- **golangci-lint v2** — `go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.6.2`

Ни tor, ни Tor Browser для тестов не нужны: `go test` без флагов не требует
ни сети, ни установленного tor (раздел 5.1 плана). Всё, что требует, живёт за
тегом сборки `integration`.

## Команды

Все команды выполняются из каталога `Source` — там лежит `go.work`.

```bash
cd Source
go vet ./core/... ./cmd/torproxy/...
go test -count=1 ./core/... ./cmd/torproxy/...
golangci-lint run ./core/... ./cmd/torproxy/...
gofmt -l core cmd          # пусто = формат в порядке
```

Модулей два — `core` и `cmd/torproxy`, — и объединены они через `go.work`.
Поэтому шаблон `./...` из корня рабочего пространства не раскрывается, и
пакеты перечисляются явно. Это не придирка линтера, а поведение `go` в режиме
рабочего пространства.

Сборка бинарника:

```bash
cd Source
go build -o ../dist/torproxy ./cmd/torproxy
```

Кросс-компиляция под другую цель — `GOOS=windows GOARCH=amd64 go build ...`,
пока в проекте нет cgo. С этапа 8 (go-libtor) для сборок под каждую ОС
понадобится родная машина или родной раннер.

## Тесты против заглушки tor

`go test` без флагов не требует ни сети, ни установленного tor. Всё, что
требует, лежит за тегом сборки `integration` и гоняется против заглушки из
прототипа — `Prototype-Python/tests/fake_tor.py`. Она изображает control-порт
с SAFECOOKIE, шлёт события BOOTSTRAP от 0 до 100 и поднимает рабочий SOCKS5.

```bash
cd Source
go test -tags integration -count=1 ./core/... ./cmd/torproxy/...
```

Нужен Python в `PATH` — больше ничего. Настоящий tor тоже не нужен:
`external.Runtime` запускает заглушку через поле `Args`, куда подставляется
интерпретатор со скриптом. Если его нет, тесты пропускаются, а не
падают. На GitHub эти тесты идут отдельным заданием.

## Граница ядра

`core` не импортирует ничего из `cmd`, `desktop`, `android`, `ios` — только
обратное направление. Проверяется дважды:

- тестом `Source/core/arch_test.go` — работает в обычном `go test`, без линтера;
- правилом `depguard` в `Source/.golangci.yml`.

У сторожа есть собственный тест на заведомо плохом файле
(`core/testdata/badimport`): молчащая проверка границы бесполезна, а
замечают это обычно поздно.

## Где проверяется

Две площадки, потому что родные раннеры Windows и macOS на gitlab.com платные,
а на GitHub бесплатные.

| Где | Что делает | Когда |
|---|---|---|
| `.gitlab-ci.yml` | `gofmt`, `go vet`, `go test`, `golangci-lint` на Linux + кросс-сборка под четыре десктопные цели | каждый push в основной репозиторий |
| `.github/workflows/ci.yml` | те же тесты на Linux, Windows и macOS + родные бинарники под все цели | push в `main` на GitHub и вручную |

Пока в проекте нет cgo, кросс-сборка честно проверяет матрицу, и GitHub —
подстраховка. С этапа 8 (go-libtor) это меняется местами: собрать под каждую
ОС можно будет только на ней самой, и родная матрица GitHub станет основной.
Она заведена заранее именно поэтому.

Intel-раннеры macOS у GitHub на практике не берутся в работу — job висит в
очереди до отмены. Поэтому `darwin/amd64` собирается на arm64-машине: Xcode
несёт SDK обеих архитектур.

## Известная местная помеха: антивирус

На машине разработки работает Kaspersky (Defender выключен), и он блокирует
тестовые бинарники Go — `go test` падает, не запустив ни одного теста:

```
fork/exec ...\b001\pkg.test.exe: Access is denied.
```

Иногда отказ приходит раньше, на записи файла (`open ...: Access is denied`),
а сам файл уезжает в карантин и исчезает с диска.

**Причина — `-buildmode=pie`.** Начиная с Go 1.26 тестовые бинарники под Windows
линкуются позиционно-независимыми, и именно на это реагирует антивирус. Проверено
2026-09-06 подряд в трёх заходах по шесть свежих пакетов: **0 из 18** с настройками
по умолчанию и **18 из 18** с `-buildmode=exe`. Ни размер пакета, ни имя файла, ни
каталог сборки (`GOTMPDIR`, включая каталог внутри проекта) на это не влияют —
всё проверено отдельно.

**Обход — один флаг:**

```bash
cd Source
GOFLAGS=-buildmode=exe go test -count=1 ./core/... ./cmd/torproxy/...
```

Флаг нужен **только для локального прогона тестов на этой машине**. В `go env -w`
его прописывать не стоит: тогда он попадёт и в сборку выпуска, а позиционная
независимость в поставляемом бинарнике — полезное свойство, терять его не за чем.
На CI ничего этого не нужно: тесты проходят на Linux, Windows и macOS штатно.

Обычные (не тестовые) бинарники антивирус не трогает: `go build` работает, и
собранный `torproxy.exe` запускается.

Совсем убрать помеху можно исключением в Kaspersky, но это ручная работа владельца
машины, и исключения **по путям её не снимают** — блокировка держится на контроле
активности программ, а не на проверке файлов. Работающий вариант — внести в
доверенные программы линковщик Go (`C:\tool\Dev\Go\pkg\tool\windows_amd64\link.exe`)
с галкой «Не контролировать активность программы».
